# 如何判断推荐推理是否有效

[返回首页](../README.md)

本页是维护者建议的阅读与实验记录框架。不同工作可能采用不同任务和协议；未核实的信息统一记录为“未核实”。

## 先确定比较的是什么

| 维度 | 需要记录 | 容易混淆的情况 |
| --- | --- | --- |
| 任务 | 全库检索、固定候选排序、重排、评分或交互推荐 | 重排的 Recall 与全库检索的 Recall 直接比较 |
| 数据 | 版本、预处理、时间切分、用户/物品数量 | 同名 Amazon 子集被当作同一实验设置 |
| 候选 | 候选来源、规模、是否注入正例、负例采样方式 | 采样负例结果被写成全库性能 |
| 训练 | 基座、参数量、样本量、训练 token 与教师来源 | 更多监督带来的收益被全部归因于预测时推理 |
| 推理 | 候选数、生成长度、采样数、搜索宽度、工具次数 | 多次采样与单次输出在不同预算下比较 |
| 结果 | 指标定义、K 值、绝对值/相对变化、随机种子 | 百分点与相对百分比混用 |

## 三层证据

以下是本仓库的记录维度，不是论文质量评分：

1. **系统效果**：整套方案优于基线，说明系统有用，但仍可能受模型、数据或候选差异影响。
2. **组件消融**：去掉推理模块、替换轨迹或调整奖励后，观察效果变化；需说明其他条件是否相同。
3. **预算控制与过程验证**：对齐训练或推理计算预算，检查中间推理与最终选择的关系，进一步区分收益来源。

例如，[OneRec-Think §5.3](https://arxiv.org/html/2510.11639v2#S5.SS3) 比较基础模型、物品对齐和加入推理的配置，可作为组件消融的阅读入口。[OneReason §8.2](https://arxiv.org/html/2606.06260v1#S8.SS2) 对齐训练 token，并在不输出推理的模式下比较不同监督，适合讨论训练期推理与预测期推理的区别。

## 强化学习论文多看一层

- 奖励来自点击、目标物品、排序指标、规则、人工标注，还是另一个模型？
- 奖励覆盖推理过程还是仅覆盖最终结果？过程奖励本身如何验证？
- 是否有保留原顺序、输出格式、热门物品偏置等获得高奖励的捷径？
- 数据构造能否接触目标答案？训练时可以使用标签，但预测输入不应泄漏测试标签。
- 是否比较 SFT、直接 RL、SFT 后 RL，以及不同轨迹质量？

[GR2 §5.4](https://arxiv.org/html/2602.07774v6#S5.SS4) 提供多种 SFT/RL 配置的重排比较；论文也讨论保留候选顺序带来的奖励投机。阅读时应同时核对候选和奖励定义。

## 推理时扩展论文多看成本曲线

建议同时记录推荐质量与以下至少一种成本，而非仅记录最优结果：

- 每请求生成 token、模型前向次数或总计算量。
- 采样数、搜索宽度、验证器调用数。
- 相同硬件、批量和缓存条件下的平均及尾部延迟。
- 对交互系统，用户轮数和工具调用成本。

离线/近线推理与在线响应应分别计时。缓存后的排序耗时不能代表包括记忆构建在内的完整请求成本。文本 CoT、潜在状态迭代和候选重排都可能增加测试时计算，但应分别标注机制。

## 可复现资源的标注

| 状态 | 含义 |
| --- | --- |
| 官方代码链接已核实 | 作者论文或项目页给出链接，仓库内容可见 |
| 作者给出链接，内容未核实 | 入口可追溯，但未能确认代码内容或下载可用性 |
| 官方模型/数据已核实 | 分别核对模型或数据页，不从代码链接推断 |
| 本仓库已复现 | 有环境、版本、命令、日志与结果记录 |
| 未核实 | 当前证据不足；不等于资源不存在 |
